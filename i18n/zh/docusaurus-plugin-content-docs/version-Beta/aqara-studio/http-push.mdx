# HTTP Push 推送

Aqara Studio 支持通过 HTTP Push 将设备数据、对象事件和告警实时推送给您。您只需在 Studio 中配置一个全局 Webhook 地址，Studio 就会以 HTTP `POST` 的方式，将消息逐条发送到该地址。

这类能力适合以下场景：
- 将设备数据同步到自建平台、数据中台或告警中心。
- 在第三方系统中接收设备新增、删除、空间变更等对象事件。

## Aqara Studio 的 HTTP Push 是如何工作的？

Aqara Studio 的 HTTP Push 采用“Studio 主动推送，第三方服务端确认”的模式：

1. 您在 Aqara Studio 中 [配置接收地址、设置响应校验规则、选择需要订阅的事件类型；必要时还可添加 Header 字段和签名配置](#在-aqara-studio-配置消息推送)。
    - 响应校验规则默认使用 **Studio 标准确认**。
    - 若仅需判断 HTTP 状态码为 200，响应校验规则可选择**仅 HTTP 状态码 200**。
2. 当您保存上述配置后，Aqara Studio 会立即向您配置的接收地址发送一条 `WebhookVerification` 消息（HTTP POST），用于验证接收地址是否可用。
3. 若您选择的响应校验规则为 **Studio 标准确认**，您需要返回一条包含 `code` 为 0 且 `challenge` 为 `WebhookVerification` 消息中 `data.challenge` 的响应消息，表示您顺利接收该消息，此地址通过验证。如此，Aqara Studio 才会正式启用 HTTP Push。
  
    若为 **其他响应校验模式**，则参考下文 [返回 WebhookVerification 响应](#返回-webhookverification-响应) 的说明编写响应消息。

    当上述验证成功后，Aqara Studio 才启用并开始业务推送；验证失败则保留原配置。
4. 当您配置的订阅事件发生时，Aqara Studio 会按上述配置向您配置的接收地址发送 HTTP `POST` 请求。

  每个请求正文只包含一条消息，消息格式为 JSON。
5. 当您接收到消息后，您需要返回一条包含 `code` 为 0 的响应消息，表示您顺利接收该消息。

:::tip
HTTP Push 是实时、best-effort 的推送机制，不提供持久化消息队列、历史补发，也不保证全局顺序。
:::

## 接收端要求

在实现 HTTP Push 之前，请先确认您的接收端满足以下要求：

- URL 必须是包含主机的绝对 `http` 或 `https` 地址，UTF-8 编码最多 4096 字节且不能包含空白，不允许 userinfo、query 和 fragment；显式端口必须在 1～65535 之间。Studio 保留路径中的连续斜杠和已有百分号转义，不跟随重定向。
- HTTPS 会校验证书链、有效期和主机名；证书必须被 Studio 所在 JVM 信任，不能关闭证书校验。
- 请求使用 `Content-Type: application/json; charset=utf-8` 与 `Accept-Encoding: identity`。需要校验正文的模式不得使用 `gzip`、`br` 等压缩响应；“仅 HTTP 状态码 200”不读取或校验正文及其编码。
- 固定 Header 名称不区分大小写，不自动添加 `X-Studio-*` 前缀；不能使用 `X-Studio-*`、`Proxy-*`、`Host`、`Content-Length`、`Transfer-Encoding`、`Content-Encoding`、`Content-Type`、`Accept-Encoding`、`Connection`、`Expect`、`TE`、`Trailer` 或 `Upgrade`。

## 支持的消息类型

Aqara Studio 会向接收端发送以下几类消息：

:::tip
下表中 `data.eventType` 是 `objectEvent` 消息的特定字段，用于区分具体事件类型，其他类型的消息没有该字段。阅读 [消息字段说明](#消息字段说明) 了解 Aqara Studio 推送消息的通用字段。
:::

| 消息类型（type） | data.eventType |发送条件 |
| --- | --- | --- |
| `WebhookVerification` |- |  endpoint 验证及熔断恢复探测。 |
| `TraitValueUpdate` | - | 设备点位值变化；“设备数据与结构事件”组合项开启时发送，默认开启。 |
| `objectEvent` |  <ul><li>`DEVICE_ADDED`（设备新增）</li><li>`DEVICE_REMOVED`（设备删除）</li></ul> | 推送启用后默认发送，不受其他订阅项影响。 |
| `objectEvent` | <ul><li>`DEVICE_ENDPOINT_ADDED`（设备端点新增）</li><li>`DEVICE_ENDPOINT_REMOVED`（设备端点删除）</li><li>`DEVICE_TRAIT_PARAMETER_UPDATE`（设备功能点属性更新）</li></ul> | 与点位值变化共用“设备数据与结构事件”组合项，暂不支持分别选择。 |
| `objectEvent` | <ul><li>`SPACE_ADDED`（空间新增）</li><li>`SPACE_REMOVED`（空间删除）</li><li>`SPACE_UPDATED`（空间更新）</li><li>`AUTOMATION_ADDED`（自动化新增）</li><li>`AUTOMATION_REMOVED`（自动化删除）</li><li>`AUTOMATION_UPDATED`（自动化更新）</li><li>`AUTOMATION_SPACE_UPDATED`（自动化空间更新）</li></ul> | 您需要自主订阅或全订阅了这些事件后，才会推送。 |
| `AlarmEvent` | - |  原始告警，默认关闭。 |

## Webhook 验证

### 接收 WebhookVerification 消息

当您根据上述步骤在 Aqara Studio 上保存 HTTP Push 配置或重新启用推送时，Aqara Studio 会先向您配置的接收地址发送一条 `WebhookVerification` 消息，用于验证接收端是否可用。

验证消息示例如下：

```json
{
  "type": "WebhookVerification",
  "version": "v1",
  "msgId": "verify-39c63800-c8c1-4f4b-b77c-57f24f0de240",
  "data": {
    "challenge": "00112233445566778899aabbccddeeff"
  }
}
```

### 返回 WebhookVerification 响应

收到 WebhookVerification 消息后，请按照 Aqara Studio 中配置的响应校验模式返回相应响应。响应通过校验后，即表示消息接收成功且该地址验证通过，说明如下：

| 模式 | 成功条件 | 响应示例 |
| --- | --- | --- |
| **Studio 标准确认（默认）** | HTTP 2xx，合法 JSON 对象，顶层整数形式的 `code=0`；验证消息还需原样返回 `challenge`。 | 业务 `{"code":0}`；验证 `{"code":0,"challenge":"请求中的值"}` |
| **仅 HTTP 状态码 200** | HTTP 状态码必须为 **200**；忽略正文，可为空或任意内容。 | 空正文 |
| **HTTP 状态码 200 + 文本匹配** | HTTP 状态码 200，完整 UTF-8 正文与期望文本完全一致，包括空格、换行；不做 trim 或类型转换。 | 期望 `ok` 时返回 `ok` |
| **HTTP 状态码 200 + JSON 匹配** | HTTP 状态码 200，合法 UTF-8 JSON 满足期望值。对象按字段递归匹配，允许响应有额外字段。 | 期望 `{"result":{"code":0}}`，允许返回 `{"result":{"code":0,"message":"ok"}}` |

若您的响应校验规则为 **Studio 标准确认**，当您收到 `WebhookVerification` 消息后，您需要返回一条包含 `code` 为 0（不接受 `"0"`、`0.0`、`0e0`） 且 `challenge` 为 `WebhookVerification` 消息中 `data.challenge` 的响应消息，表示您顺利接收该消息，此地址通过验证。如此，Aqara Studio 才会正式启用 HTTP Push。

```json
{
  "code": 0,
  "challenge": "00112233445566778899aabbccddeeff"
}
```

后三种模式仍须支持 `WebhookVerification`，但无需返回 `code` 或 `challenge`，只需满足所选规则。
- **仅 HTTP 状态码 200**：无法区分成功和以 HTTP 状态码 200 返回的业务错误，此类响应会被视为成功、不再重试。它也不验证接收端是否识别了验证消息；应另行确认地址及接收逻辑正确。
- **JSON 匹配模式**：支持对象、字符串、数字、布尔值和 `null`，区分类型，但数字按数值比较（`0` 与 `0.0` 相同）；缺失字段不等于 `null`。不支持数组作为期望规则、正则或脚本；额外响应字段可以包含数组。JSON 字段顺序和格式化空白不影响匹配。JSON 期望最多 16 层、256 个值，禁止重复字段。
- **文本匹配模式**： 文本期望 `0` 不匹配 `0.0` 或 `"0"`；JSON 字符串期望值则必须带双引号，例如 `"ok"`。期望正文最多 4096 UTF-8 字节。文本模式留空表示要求空响应。

:::note
`WebhookVerification` 消息不重试。如果验证失败，当前配置不会生效。
:::

## 请求格式

Studio 向接收端发送请求时，具有以下固定特征：

- 请求方法为 `POST`。
- 默认 `Content-Type` 为 `application/json`。
- 每个请求正文只包含一条消息。
- 响应也在同一条 HTTP 请求中返回。
- 您在 Aqara Studio 中配置的 Header 字段，会按名称和值原样发送。

### 请求头

HTTP Push 请求头至少包含以下字段：
| Header | 说明 |
| --- | --- |
| `X-Studio-Delivery-Id` | 每次投递的唯一标识，格式为 UUID |
| `X-Studio-App-Key` | AppKey 字段。若您在 Aqara Studio 上配置了 AppKey 和 AppSecret 时，请求头才会包含此字段。 |
| `X-Studio-Time` | 时间戳。若您在 Aqara Studio 上配置了 AppKey 和 AppSecret，请求头才会包含此字段。 |
| `X-Studio-Nonce` | 32 位小写十六进制随机数。若您在 Aqara Studio 上配置了 AppKey 和 AppSecret，请求头才会包含此字段。 |
| `X-Studio-Sign-Version` | 签名版本。若您在 Aqara Studio 上配置了 AppKey 和 AppSecret，请求头才会包含此字段，固定为 `v1`。 |
| `X-Studio-Sign` |  签名（HMAC-SHA256 小写十六进制结果）。若您在 Aqara Studio 上配置了 AppKey 和 AppSecret，请求头才会包含此字段， |

### 验签规则

若您在 Aqara Studio 中配置了 AppKey 和 AppSecret，接收端应使用 AppSecret 校验请求头中的 `X-Studio-Sign`。

用请求中的明文信息 **重新拼出** [签名原文](#签名原文)，再用同一 AppSecret 计算 HMAC，与 `X-Studio-Sign` 比对。AppKey 本身已通过请求头 `X-Studio-App-Key` 明文下发，如需确认是否为本端配置，可直接与本地 AppKey 比较；完整性与防篡改仍依赖签名校验。

#### 签名原文

签名原文（`signingString`）由以下 6 行 UTF-8 文本按顺序组成，行与行之间使用 `LF`（`\n`）连接，末尾不加换行：

```text
v1
AppKey
Delivery-Id
Time
Nonce
SHA256(raw-body)
```

各行取值如下：

| 行内容 | 说明 |
| --- | --- |
| `v1` | 对应 `X-Studio-Sign-Version` |
| `AppKey` | 对应 `X-Studio-App-Key` |
| `Delivery-Id` | 对应 `X-Studio-Delivery-Id` |
| `Time` | 对应 `X-Studio-Time` |
| `Nonce` | 对应 `X-Studio-Nonce` |
| `SHA256(raw-body)` | 原始请求体的 SHA-256 小写十六进制值 |

#### 推荐验签步骤

1. （可选）将 `X-Studio-App-Key` 与本地配置的 AppKey 比较，不一致可直接拒绝。
2. 按上表用请求头与原始请求体拼出 `signingString`。
3. 用 HmacSHA256 算法生成签名，算法密钥是配置的 AppSecret 值，输出小写十六进制字符串。
4. 与请求头 `X-Studio-Sign` 做比较；一致则验签通过。

:::tip
发生重试时，消息正文和 `X-Studio-Delivery-Id` 保持不变，但 `Time`、`Nonce` 和 `Sign` 会重新生成。
:::

### 消息字段说明

HTTP Push 请求消息的通用字段如下：

| 字段 | 说明 |
| --- | --- |
| `type` | 消息类型，当前支持 `WebhookVerification`、`TraitValueUpdate`、`objectEvent` 和 `AlarmEvent`。如需了解各类型消息的发送条件，清参考 [消息类型](#支持的消息类型) 的说明。 |
| `version` | 当前仅支持 `v1` |
| `msgId` | 消息标识，用于链路追踪 |
| `data` | 业务数据主体，根据 Type 不同，数据结构不同。<ul><li>若 type 为 `WebhookVerification`，`data` 内为 `challenge` 字段，示例请见 [接收 WebhookVerification 消息](#接收-webhookverification-消息)。</li><li>若 `type` 为其他，data 内结构复用了 [WebSocket 同名响应的 data 结构](./../aqara-developer/data-export-api/websocket-api/index.mdx)。<ul><li>若 type 为 `objectEvent`，您需要通过 `data.eventType` 确定具体事件类型。</li></ul></li></ul> |
| `code` | 处理结果码，`0` 表示成功 |
| `message` | 处理结果描述 |

## 响应格式

###  响应内容

响应体至少应包含：

```json
{
  "code": 0
}
```

如果处理失败，可以返回非 0 的 `code`：

```json
{
  "code": 1
}
```

### 响应体限制

业务请求正文上限由 Studio 部署配置，最大不超过 64 MiB；超限消息不会投递。接收端应按自身容量设置入站正文限制，并以实际部署约定为准。

更多要求如下所示：
| 限制项                | 具体要求                                                                                     |
|---------------------|--------------------------------------------------------------------------------------------|
| 响应是否压缩             | 需要校验正文时，响应**必须未压缩**                                                          |
| 响应正文大小上限          | 65536 字节（已部署 Studio 实际限制可能更小）                                                |
| 响应 Header 项数上限      | 所有模式下 Header 最多 16 项                                                               |
| Header 单行最大长度       | 4096 字节                                                                                  |
| 标准模式 JSON 嵌套层级上限 | 128 层                                                                                   |
| JSON 匹配模式嵌套层级上限 | 16 层                                                                                    |
| JSON 匹配模式解析值上限   | 1024 个                                                                                   |
| 数字文本最大字符数         | 128 字符                                                                                  |
| 是否允许重复字段           | 禁止重复字段                                                                              |

接收端应只返回确认所需的少量内容。**仅 HTTP 状态码 200** 不读取正文，不受正文大小限制，但仍受连接、响应头和超时限制。

## 重试与熔断

单条业务消息最多发送两次。连接/读取失败、408、429、5xx、2xx 非法确认可重试；普通等待 1 秒。429 的 `Retry-After` 只接受 0～30 秒整数；其他值按 1 秒。其他 4xx 和 3xx 不重试。

Studio 在 2 秒内无法建立连接会判定该次请求失败；单次 HTTP 调用采用 5 秒的超时取消期限。逻辑投递窗口从进入发送阶段起计算，为 45 秒，不包含此前的排队等待；窗口到期后不再启动重试。这些期限不是端到端送达或底层资源立即释放的保证：DNS 等底层操作不响应取消时，实际结束可能更晚。

每次 endpoint 验证只发送一次 HTTP 请求，不做当场重试。熔断后到达下一个退避时间点时，Studio 会发起一次新的 `WebhookVerification`；验证成功后才恢复业务推送。

`X-Studio-Delivery-Id` 是每次逻辑投递的 UUID，重试保持不变。正文 `msgId` 仅用于业务追踪，不能代替幂等键。开启签名时，建议使用 `(X-Studio-App-Key, X-Studio-Delivery-Id)` 作为持久化联合唯一键。未开启签名且同一接收服务对接多个 Studio 实例时，应增加双方约定的固定实例标识 Header，并与 Delivery-Id 组合使用。幂等记录与业务结果/可靠入库任务应在一个事务内落地，再确认成功。网络超时可能发生在第三方已处理之后。

这是实时 best-effort，不保证全部到达，不补发历史，也不保证到达或处理顺序。队列溢出或 endpoint 暂停期间的消息可能丢失；需要状态完整性的第三方应结合现有查询接口做周期性校准。协议不要求额外的补偿确认握手。

## 订阅与默认推送规则

启用 HTTP Push 后，消息的推送行为遵循如下规则，无需全部事件手动勾选：

| 类别 | 规则说明 |
| --- | --- |
| `DEVICE_ADDED` / `DEVICE_REMOVED` | 默认发送，始终推送，配置无法关闭，不受其他订阅项限制 |
| `TraitValueUpdate` | 设备点位数值变化；归属于“设备数据与结构事件”组合选项，默认开启 |
| `DEVICE_ENDPOINT_ADDED` / `DEVICE_ENDPOINT_REMOVED` | 与 `TraitValueUpdate` 共用“设备数据与结构事件”组合项，暂不支持独立订阅，默认开启 |
| `DEVICE_TRAIT_PARAMETER_UPDATE` | 亦与“设备数据与结构事件”组合项共用，默认开启 |
| 可配置对象事件 | 当前支持逐项勾选的 8 个对象事件，默认全选，可全部取消 |
| 告警事件 `AlarmEvent` | 默认关闭，可选启用 |

:::tip
- “全订阅”模式不仅覆盖当前全部对象事件，也会自动包含未来新增的对象事件；接收端应做好对未知事件类型和新数据结构的兼容（记录并忽略未支持事件，而非因未知事件拒绝整个请求）。
- 即使取消所有可选项，`DEVICE_ADDED` 和 `DEVICE_REMOVED` 仍会推送。
- 若关闭 HTTP Push，所有事件推送均会停止。
:::

## 接收端实现建议

为了让 HTTP Push 更稳定，建议您的接收端遵循以下实践：

- 优先做到“快速接收、异步处理”，避免在 5 秒超时窗口内执行耗时业务。
- 以 `X-Studio-Delivery-Id` 作为投递链路追踪字段，并结合业务状态做幂等处理。
- 不要依赖全局顺序，也不要假设一定能收到历史补发。
- 开启签名时，务必使用原始请求体参与摘要计算，不要使用格式化后的 JSON。
- 对 `WebhookVerification` 单独处理。若您的响应校验规则为 **Studio 标准确认**，确保 `challenge` 原样返回。

## 故障恢复

连续投递失败时，Studio 会暂停业务推送，并在逐步延长的等待后再次发送 `WebhookVerification` 探测恢复。

验证成功后恢复业务推送，但不补发停止期间的消息。重新启用或 Studio 服务重启后也会重新验证；验证成功前不会发送业务消息。接收端不需要实现额外的恢复确认流程。

## 示例

下面是一个典型的推送与确认示例。

### Studio 推送请求

```http
POST /hook HTTP/1.1
Content-Type: application/json
X-Studio-Delivery-Id: 0c9c109a-e724-469c-ae96-1f96e824c127

{
  "type": "WebhookVerification",
  "version": "v1",
  "msgId": "verify-39c63800-c8c1-4f4b-b77c-57f24f0de240",
  "data": {
    "challenge": "00112233445566778899aabbccddeeff"
  }
}
```

### 接收端返回确认

以下为 **Studio 标准确认** 的响应示例：

```http
HTTP/1.1 200 OK
Content-Type: application/json

{
  "code": 0,
  "challenge": "00112233445566778899aabbccddeeff"
}
```
